# Everloot 0.3.2 — profession and own-auction beta check

Addon 0.3.2 moves the profession windows and the auction-purchase reading to the game API that
Forever (client 1.60.1, interface 16001) ships. The automated tests use a mock of that API; this
list is the part only the game client can settle. Keep your SavedVariables file before installing.
Nothing here plays the character, crafts, trains, buys or posts.

## What the build's own files say

Checked on build 1.60.1.70450 (product `wow_classic_beta`), read from Blizzard's CDN by file name:
the API documentation addon (`Blizzard_APIDocumentationGenerated`, 642 files) and the Lua of the
profession, trainer, mail and auction-house windows. The documentation lists which calls exist and
their signatures. A call missing from it can still exist: the windows' own code uses several.

| Call | In the generated API documentation | Used by Blizzard's own window code in this build |
| --- | --- | --- |
| `C_TradeSkillUI.GetBaseProfessionInfo`, `GetChildProfessionInfo` | yes | yes |
| `C_TradeSkillUI.GetRecipeInfo`, `GetRecipeSchematic` | yes | yes |
| `C_TradeSkillUI.GetFilteredRecipeIDs` | **no** | yes (profession window recipe list) |
| `C_Item.GetItemNameByID` | yes | yes (auction buy dialog) |
| `C_Item.RequestLoadItemDataByID` | yes | not seen in the files read |
| `GetProfessions`, `GetProfessionInfo` | no (global functions) | yes (profession book) |
| `GetNumTrainerServices`, `GetTrainerServiceInfo`, `GetTrainerServiceSkillReq`, `GetTrainerServiceCost`, `GetTrainerServiceStepIndex` | no (global functions) | yes (trainer window) |
| `C_AuctionHouse.PlaceBid`, `StartCommoditiesPurchase`, `ConfirmCommoditiesPurchase`, `GetAuctionInfoByID` | yes | yes |
| events `TRADE_SKILL_SHOW`, `TRADE_SKILL_LIST_UPDATE`, `TRADE_SKILL_DATA_SOURCE_CHANGED`, `TRADE_SKILL_CLOSE`, `TRAINER_SHOW`, `TRAINER_UPDATE`, `COMMODITY_PRICE_UPDATED`, `COMMODITY_PURCHASE_FAILED` | yes | yes, except `TRAINER_SHOW`, which the files read do not name |
| `GetTradeSkillInfo`, `GetNumTradeSkills`, `GetCraftInfo`, `CRAFT_SHOW` (the old windows) | no | not in the files read |
| `GetInboxInvoiceInfo`, `GetInboxHeaderInfo`, `TakeInboxMoney`, `GetSendMailPrice` | no (global functions) | yes (mail window); invoice now also returns `count` and `commerceAuction` |
| `GetAuctionItemInfo`, `GetNumAuctionItems`, `PlaceAuctionBid` (the old auction house) | no | not in the files read |

Two facts shaped the code. Forever's profession window is the modern one (a `C_TradeSkillUI`
recipe list with a schematic per recipe), and the old trade-skill and craft calls are absent from
the documentation and from the window code read. Absent there does not prove they are removed from
the client, so the checklist below is what settles it.
Forever's trainer window still uses the global trainer functions, but `GetTrainerServiceInfo`
returns name, service type, texture, required level, sub-text and category in that order. The old
addon read the third value as a category.

The owned-auction calls (`GetNumOwnedAuctions`, `GetOwnedAuctionInfo`, `GetOwnedAuctions`,
`QueryOwnedAuctions`, event `OWNED_AUCTIONS_UPDATED`) exist in the documentation and in the auction
house's own code. The gold module did not read the player's own listings: it read the listing being
bought, with the old `GetAuctionItemInfo`, so its buyout attribution recorded nothing. 0.3.2 reads
the listing with `C_AuctionHouse.GetAuctionInfoByID` instead and does not use the owned-auction calls.

## In the client

1. Install the 0.3.2 zip over the old one, enable it, `/reload`, run `/everloot status`. Record the
   build (expected 1.60.1.70450) and the addon version (0.3.2). The `professions` line should say the
   trade-skill window and the trainer window are `ready`. If it says `missing ...`, copy the line:
   that name is the call this client does not have, and the module records nothing until it does.
2. Run `/dump select(4, GetBuildInfo())` and write down the interface number (the toc says 16001).
3. Open a profession window (any profession you have). Run `/everloot status` again. The `professions`
   line should report the profession, your rank, how many recipes were listed and how many new rows.
   Log out and open the SavedVariables file. Expect one `recipe_observed` row per listed recipe, with
   the colour the window showed, the product item id and the reagents with counts. Write down two
   colours and two reagent lists by hand and compare.
4. Check the cases the code treats specially:
   - A recipe whose reagent can be several items: its row has no reagents (the addon does not guess).
   - An enchant: it has no `productItemId`.
   - A profession whose window shows a rank of 0/0: the rank should still come from the profession
     book (the status line says `nothing recorded: no skill level` when it cannot).
5. Reopen the window at the same rank: no new rows. Skill up once and reopen: new rows at the new rank.
6. Open a profession trainer. Expect one `trainer_seen` row per recipe it lists, with the required rank
   and the cost the window showed; class spells and the "next step" row produce none, and reopening
   adds nothing. Write down two required ranks by hand.
7. Auction purchases, with a copper amount you can read off the window. Each is a real purchase you
   make yourself; the addon only watches.
   - Buy one item listing at its buyout (a gear or recipe listing): expect one `auction_spend`
     money event with the buyout.
   - Place a plain bid below the buyout: expect nothing.
   - Buy a commodity (cloth, herbs): expect one `auction_spend` with the total the confirm window
     showed. If the price moves while the window is open and you accept the new price, expect the new
     total, or nothing if the money that left differs from the quote.
8. Take the money from an "Auction successful" letter: expect one `auction` money event with the sale
   minus the house cut. This path did not change, but the mail window's `GetInboxInvoiceInfo` now
   returns two more values, so check it once.
9. Run `/everloot selftest` and keep the lines. Log out, keep the file, and preview it at `/upload`
   before sending.

Report any `missing ...` name from step 1 or 3 and any step that records a different number than the
window showed. A mismatch in step 7 is worth a screenshot of the confirm window and the row.
